# 6-6 首页导航逐分类商品对照、修复与复测

## 目标与执行方式

你现在要**真正进入参考站与当前 Shopify 站的首页顶栏，逐层展开并点击所有范围内的商品分类**，确认每个分类都能打开正确的 Collection/PLP，商品可以正常呈现，且实际归类效果与原站一致。**不要只检查 Collection 是否存在、总数是否接近、单个截图是否相似或首页推荐商品是否正确。**

默认对当前已授权的 Draft Theme 运行；本专项可以独立通过 `运行6-6` 执行，也是 FAST `6-1` 必须自动运行的子任务。先读取 `AGENTS.md`、`EXECUTION_RULES.md`、`04-catalog/4-4-创建分类.md`、`05-customization/5-2-功能削减.md` 和当前项目的 `PROJECT_MEMORY.md`。从项目配置确认目标原站、Shopify 店铺、主题 ID、权限与已有抓取快照；不要套用其它项目地址、商品数或分类规则。

## 1. 发现导航与确定基准

1. 分别打开**原站首页**和**目标站首页（指定 Draft Preview）**，在桌面 1440px 和移动 390px 真实浏览器里展开 Header、Mega Menu、下拉菜单与移动抽屉。收集所有实际可点击的一级、二级、三级及更深的商品分类入口（含专题集合，如 New Arrivals / Best Sellers / Sale）；记录原站层级、可见名称、源 URL、目标 URL、Collection handle/GID 与对应关系。
2. **逐条遍历菜单入口**，即使若干入口指向同一 Collection，也要分别确认点击目标正确；成员验证可按最终 Collection URL 去重，但必须保留所有来源入口的映射。一级入口若只是展开菜单，不强求它有独立 Collection；每个真正通往商品列表的入口都必须检查。
3. 基准优先使用原站此刻可访问的完整分页商品成员、`4-1` / `4-4` 保存的原站快照与稳定商品标识。保存基准时间和版本，并区分原站动态变更、商品缺货/下架、当前已导入商品、业务明确排除项。遇反爬、登录或接口不可访问，记录具体失败入口和 `blocked`，不能假称原站已对照成功。

## 2. 对每个分类执行前台双站检查

对导航清单里的**每一个商品分类**，依次完成并留下可复验的浏览器和数据证据：

1. **进入原站分类页**：记录分类名称、路径、筛选与子分类含义，实际翻遍分页 / Load More / 无限加载，得到可访问商品的完整稳定标识集合；必要时结合站点公开接口、源商品数据和原站商品详情验证语义。
2. **点击目标站首页对应导航项**：确认跳转的是正确 Collection 而非 `collections.all`、首页、空白页或错误分类，检查桌面/移动实际加载；分页、Load More、过滤、排序、返回恢复状态都要正常，不能只确认 HTTP 200。
3. **检查商品正常显示**：核验该分类所有分页/批次均可呈现实际已发布商品，不漏页、不重复加载、不出现空卡、坏图、错误标题、错误价格/变体或明显卡片渲染故障；检查页面商品总数与全量成员清单一致。对典型图片/变体/售罄交互做浏览器实测，全部商品用数据与资源读回覆盖，避免因数量多只抽检第一页。
4. **核对分类归属**：以源商品标识 ↔ Shopify handle/ID 映射，对该分类计算原站与目标站的 `missing`（原站在此分类但目标缺失）和 `extra`（目标在此分类但原站不在），并结合品类含义检查商品类型、性别、子品类、用途和专题集合条件是否符合原站。同一商品允许属于多个分类，不能因为其他分类有此商品就算当前分类合格。
5. **特殊分类单独判定**：`New Arrivals`、`Best Sellers`、`Sale`、按品牌/性别/场景划分的集合，以原站实际分类/专题成员依据为准；不能因为本站做了全站折扣就把全部商品归入原站 Sale，不能用标题关键词、宽泛 Product Type 或封面图猜测归属。
6. **不要求排列一致**：源站与本站的商品卡片顺序、默认排序可以不同，只要对应分类的实际归属一致、商品可正确访问和展示。不要因为顺序不同认定失败，也不能因两站数量相同便认定通过。动态/不可稳定重现的源站集合须注明比较范围与依据，不声称 100% 一致。

## 3. 发现差异必须自主修复

- 将问题区分为导航指向错误、Collection 规则/手动成员错误、源商品未导入、分类 Tags / Type / Metafields 不准确、商品未发布、筛选/分页缺陷、模板/卡片渲染或媒体故障。先从原站证据查明**原因和受影响的全部商品及分类**。
- 在当前已有授权范围内执行：必要时复用 `4-3` 按差集幂等补导；按 `4-4` 修正原生 Shopify 分类字段、Collection 条件、成员和菜单指向；主题视觉、商品卡片、分页、过滤问题按 `3-1` 或对应页面专项修复并部署到同一 Draft。修改后必须远端读回，重新打开受影响分类及相邻分类完成**全量成员对账 + 桌面/移动前台复测**。
- **禁止**用主题里硬编码商品 ID、只隐藏不合适的卡片、全目录兜底、杜撰分类字段或随意删掉商品/标签来制造看似正确的结果；禁止重复导入已存在商品。商品/Collections/Menus 为可能影响 Live 的共享数据，修改前核实操作权限及影响范围，**不修改 Live Theme、不擅自发布或开放店铺**。
- 发现可修复问题就继续修复与复验，不只写修复建议就结束。限流与临时故障有限重试；真实权限或原站不可访问时记录 `blocked`、证据和最小恢复操作，同时完成所有不依赖它的分类。不能把 `blocked` / `not_run` 算作通过。

## 4. 逐分类验收清单和最终报告

在**当前 Shopify 项目**内记录并更新 `TASK_CHECKLIST.md`、`PROJECT_MEMORY.md`，附带可追踪的分类对照结果（例如 `agent-evidence/category-comparison.json` 和 `agent-evidence/category-comparison.md`，复用已有等价文件亦可）。每个分类至少包含：

- 导航路径、原站/本站 URL、Collection handle/GID、原站快照时间、两侧成员总数与实际遍历页数；
- `source_handles / target_handles / missing / extra` 或对应可追溯数据文件、分类语义判断与商品展示/坏图/分页/筛选状态；
- Desktop/Mobile 实际点击结果、错误样例、根因、修复记录、远端读回、复验时间、`verified / failed / blocked / not_run / excluded`。

**通过标准：**本项目范围内每一条导航入口都正确，每个可访问的商品分类全量成员符合原站分类效果（不比较商品排列），无未解释的错误归类、缺失商品或前台展示故障，桌面与移动端均已实际核验；已修改的分类完成复测。若有源站动态变动，按有时间戳的同一基准列清楚差异；尚未验证的入口或无法访问的原站不能宣称“全部通过”。

最终用简短汇总明确：导航入口总数/已测数、唯一分类总数/通过数、原站与目标站分类成员差集总数、前台坏图/空卡/分页异常数、已修复/未修复/阻塞数、Draft/Live 各自状态和逐分类证据路径。**仅当全部适用项真实通过时才能报告本专项完成；否则报告 partial/blocked，并保留剩余工作。**

直接开始对照、修复和复测，不要只输出计划，也无需等用户逐步下指令。
