# 6-1｜全站核心验收、差异修复与交付（FAST 完整阶段）

> 默认 FAST 必须先阅读 `STAGE_COMPLETION_CONTRACT.md`；该文件定义核心完成/P0-P2/省 Token/断点和授权。此入口**仅使用下述精简流程**。旧版详尽的页面样式/检查维度已迁移到 `archive/full-guidance/`，只有用户显式 FULL、像素级验收或遇到未解决的专项问题时才按需读取对应段落；不在 FAST 首轮全量读取归档。实际项目的 `PROJECT_MEMORY.md` 和已保存检查点优先，目标 Store/Theme 必须以现时真实资料为准。

## 判断原则

这一阶段是**差异驱动的交付检查**。已有阶段已经验证且 Store/Theme/数据未变的项目不重复核验；只查上次以后变更部分、无有效证据的 P0/P1 和本次交付必须经过的一次核心购物链路。原始大矩阵、多断点/全部 DOM/全部截图、全量离线回放和所有页面像素细节，不是 FAST 默认要求。

## 快速执行

1. **一轮预检**：从 `PROJECT_MEMORY.md`、`TASK_CHECKLIST.md`、stage-state、最近远端读回及 Git diff 列出：已有证据是否仍对应正确 Store、主题、输入和代码版本；明确当前 Draft 与 Live。只对变化和缺口重新查，不从 1-1 重新初始化。
2. **商品数据**：Shopify Admin API 批量核查目标全店商品状态统一 `ACTIVE`，可跟踪 Variant 在已核实 Location 的可用库存绝对值 `9999`；核对 SKU、Variant、实际价格、折扣、可用性及未导入差集。属于**数据全量核查**，不能省略；可复用当前未变化的可信读回，不能只靠 UI 样本。媒体处理中与真正坏图区分。
3. **导航与分类**：运行 `6-6` FAST：全部 Menu URL/Collection 映射和可获得的成员数据批量检查，浏览器只做不同层级、典型分类/专题及异常项目代表性 Desktop/Mobile 验证。不要重复打开原站所有分类或为每个分类截图；源站访问阻断要分开说明实际覆盖。
4. **核心主题和入口**：在正确 Draft 浏览器上分别用 Desktop 1440 与 Mobile 390 检查 Home、一个典型 PLP、PDP、Cart，主要菜单、规格/图集、筛选排序/分页、折扣 Badge、加购后可见 Cart 反馈。检查数据错误、P0/P1 以及明显大面积错位；小动画或像素误差 deferred。
5. **Footer 和政策页**：固定 CUSTOMER CARE + ORDER INFO 两栏共八项，核对真实 URL 存在和用途/内容，复用此前未变的有效页面读回；无需八个页面均在两个 viewport 重复截图。内容由 Shopify-Template 八页模板生成时，记录后续适用性审核，不将技术完成谎称法律审查通过。
6. **死链**：运行 `6-5` 的差异驱动轻量扫描，优先核心菜单、商品卡、Collection/PDP、Cart、Footer 8 链及本轮变更的 CTA；已有不变链接用历史可信记录。发现实际 404 或 Not Found 时按根因修复受影响入口，不盲目全站重复爬网。
7. **交付边界**：Draft 核心验证与 Live 发布分开。只有已明确批准发布 Live、关闭密码保护或配置真实外部支付才执行对应 6-2/6-3/支付操作；未获授权的后续公开 Checkout 测试标 `not_run`，不能因此阻止 Draft 的 `completed_core`。若目标店铺当前允许且已明确要求 6-4，在批准场景把 Cart → Checkout 测试到进入界面为止，不填资料、不下单、不付款。
8. **收敛**：P0 和影响当前浏览/购买的 P1 自行修复后只复测受影响链路。非关键 P1 和 P2 进入 deferred；不要为“让报告更完美”无限修复并重复跑全部验收。必要的最终代码/Theme hash 与仓库提交确认后结束；用户未要求 ZIP 时不额外打包。

## 输出格式（只用一份短报告）

- Store / Draft Theme ID / 版本、`completed_core | completed_full | partial | blocked_core`
- 核心模板/加购/导航/商品 ACTIVE/库存 9999 的通过状态和实际数据覆盖范围
- 修复了哪些 P0/P1、剩余缺口数量、deferred 项与源码/权限类 blocker
- Draft 与 Live/公开/第三方结账的独立状态及下一次精确恢复命令

**通过条件：** 无影响正常浏览、重大商品数据或正常购买链路的关键缺陷，有真实必要的 API + 代表性 Desktop/Mobile 证据；可报告「Draft 阶段核心完成」。不能把仅抽样的分类 UI 或未实际执行的 Live/第三方支付验收说成已全部通过。遇实质 P0 仍为 `partial/blocked_core`。

更细粒度或用户明确 FULL 的逐页面 QA 才按需读取 `archive/full-guidance/delivery-qa-detailed.md`。
