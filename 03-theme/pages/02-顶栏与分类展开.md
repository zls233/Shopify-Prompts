# Shopify 顶栏与分类展开层复刻

你现在需要完善当前 Shopify Theme 的顶栏（Announcement Bar、Header、主导航）及其分类展开层（Mega Menu / 下拉菜单 / 移动端分类导航）。目标是基于当前项目已采集的 reference 和目标原站，逐项校准结构、视觉、内容、链接和交互，尽可能与原站一致。不要重新设计，也不要只做一张静态截图。

## 目标与边界

执行前确认并记录：

```text
TARGET_SITE_URL={{TARGET_SITE_URL}}
TARGET_STORE={{TARGET_STORE}}.myshopify.com
DRAFT_THEME_ID={{DRAFT_THEME_ID}}
TARGET_NAV_ITEMS={{TARGET_NAV_ITEMS}}
```

`TARGET_NAV_ITEMS` 可填“全部”或指定一级分类。只修改这些分类涉及的顶栏、展开层及必要配置；不要顺手重做首页、商品列表、Footer 或无关商品数据。先读取 `05-customization/02-功能削减.md`，以它为功能排除的唯一权威清单；原站存在但项目明确排除的入口不加入。`05-customization/04-粘性顶栏.md` 只适用于原站确有对应滚动行为的情况，不要直接套用其具体层级假设。

实时核对目标店铺、执行身份、当前 Draft/Live Theme ID 和角色。默认只修改与同步到指定 unpublished Draft Theme，未经明确授权不修改或发布 Live。若需写入 Shopify Menus、Collections、Metaobjects 或内容资源，先复核 `01-project/02-建站授权准备.md` 的权限与资源归属；缺少权限时报告阻塞，不用前端硬编码绕过。保留工作区已有未提交改动。

## 一、采集基准并审计现状

先读取项目已有的 `site-reference-summary.md`、`manifest.json`、`references/`、Desktop/Mobile 截图和 SingleFile/WebArchive/HTML，再实际检查原站和 Draft 预览。记录 reference 采集时间、现站观察时间、页面 URL、视口尺寸及两者差异；有冲突时说明采用哪个版本，不混用不同时期的菜单文案与图片。

至少观察首页、一个目标分类页及分类展开状态，分别检查 Desktop、窄桌面、Mobile；原站无法访问时明确标注无法现场核验的项目，仅据已归档证据实施。

逐层记录：

- Announcement Bar、Logo 区、搜索、工具入口、主/次导航的顺序、高度、最大宽度、左右间距、边框、字体、图标、Logo 资源和点击目标。
- 每个一级分类展开的触发方式（hover、click、focus、touch）、打开延迟、关闭条件、定位、宽高、列数、列顺序、标题、子项、图片、促销块及 CTA。
- 展开层相对于 Header 的位置、覆盖还是推动内容、背景/遮罩、阴影、层级、滚动和边缘位置；鼠标从触发项移入面板时是否保持展开。
- Mobile 菜单的入口、抽屉/全屏布局、分类逐级展开和返回、关闭按钮、遮罩、滚动锁定及图文顺序。不要把桌面 hover 菜单直接缩到手机。
- 滚动时各层是否 sticky、隐藏或恢复；从页面顶部到滚动后的状态与断点变化。

审计 `sections/`、`snippets/`、`assets/`、`layout/theme.liquid`、`config/`、Header 所用 Menu 和相关 JavaScript，区分 Theme 渲染/CSS/交互、菜单配置、Collection/内容资源、外部素材与项目排除项。先整理一张“原站证据 -> 当前 Draft -> 差异 -> 修改归属”的清单，再动手实现。

## 二、导航数据与链接

对每个可见分类和展开项记录标签、层级、原站 URL、目标 Shopify 资源与 URL、资源存在及发布状态、实际访问结果。不要因为路径形状正确、Menu item 存在或返回 HTTP 200，就认为目标 Collection 或页面内容正确。

优先复用现有 Shopify Navigation Menu，使用 `section.settings.menu.links`、`link.links`、`link.object`、`link.url`、`link.title` 驱动可维护的分类层级；不要同时维护一份硬编码 JavaScript 导航树。菜单的层级、标题、顺序和 `resourceId` 应与真实 Shopify Collection/Page 对应。展开层独有的图片、文案与推广块优先沿用当前主题设置或已有 Metaobject 模式，只有确实需要商家维护且现有结构不足时才增设结构化资源。

若商品分类、Collection 成员或 Menu 本身错误，按 `04-catalog/04-创建分类.md` 核对并修复数据归属，不用 Liquid 标题匹配或 CSS 隐藏错误项。确认 Collection 和目标商品分别已发布到 Online Store。站内内容页缺失时按 `03-theme/pages/05-页面补齐.md` 的资源流程处理，或将对应入口标记为交付阻塞；本轮未获内容资源授权时不得擅自创建。不要将链接指向 `#`、空 `href`、`javascript:void(0)`、首页兜底或已知 404。仅当原站确为非导航型展开按钮时，使用语义化 `button`，不要伪造链接。

## 三、实现顶栏与展开层

在现有 Header 组件上做最小范围调整，保留当前主题的搜索、购物车等真实功能及其原有事件。逐项对齐：

- 各层尺寸、容器对齐、Logo 实际素材及宽高、导航组中心、间距、字体与图标；在窄桌面检查不挤压搜索与右侧工具区。
- 展开层的列布局、媒体比例和裁切、行距、背景、边线、遮罩、动画时长，以及打开时不遮挡必须操作的控件。
- 原站实际 sticky/隐藏逻辑及高度占位；滚动前后不跳动、不重叠、不产生额外空白。不要假定整组 Header 必须固定。
- Desktop 指针、键盘及触摸设备的状态一致性。触发按钮使用准确的 `aria-expanded`、`aria-controls`；键盘可打开并进入面板，Escape 可关闭并将焦点返回触发项，Tab 不被困住；焦点与 hover 离开时正确收起。
- Mobile 菜单能逐级进入与返回，点击最终链接正常跳转；关闭、Escape、遮罩和浏览器返回按原站行为处理，关闭后恢复滚动与焦点。尊重 reduced-motion，避免展开层闪烁或页面横向溢出。

原站没有的交互、分类或推广内容不要为了“完整”而补造；项目明确削减的入口不要仅用 CSS 隐藏。复用现有 icon、字体和图片资产，不用 Unicode 字符模拟工具图标。

## 四、验证与交付

完成后运行项目已有的静态检查（包含适用的 `shopify theme check`），仅同步本轮相关文件到指定 Draft，并读回或检查 Draft 实际输出。用真实浏览器在至少 1440px 桌面、窄桌面和 390px 手机视口对照原站与 Draft；核对 bounding box、computed style、展开层截图及滚动状态。逐一走通目标一级分类、二/三级链接、搜索/购物车等相邻控件、键盘与触摸菜单、Escape/关闭、页面滚动和浏览器前后退。抽查目标 URL 返回的真实资源与分类商品，不以截图或 Theme Check 通过替代交互与数据验证。

最后报告：原站/reference URL 与观察时间、目标店铺和 Draft/Live 角色、修改的文件与菜单/资源、Desktop/Mobile 差异与验证结果、每条未完成或不可用的导航目标、权限/资源阻塞，以及 Live 是否保持未修改。不要输出 token 或密钥；无法验证的项目明确标为未验证。
