# Shopify 建站授权准备：CLI、Admin GraphQL 与 Theme Access

在首次写入 Shopify 店铺资源之前执行本 Prompt。商品导入、商品分类与自动 Collections、Menus、发布渠道、Metaobjects、Files、库存，以及创建或更新 Pages / Blogs / Articles，都应先完成这里的检查。项目初始化时预计会做这些工作，也应提前执行一次。后续任务先复核本次结果；店铺、应用、权限或凭据发生变化时重新执行，不要每次重建应用。

## 输入与目标

- 目标店铺：`{{SHOPIFY_STORE}}`，必须是准确的 `*.myshopify.com` 域名。
- 项目路径：`{{PROJECT_PATH}}`。
- 计划操作：`{{PLANNED_OPERATIONS}}`。如尚未确定具体页面或商品，按完整建站处理。
- 是否需要 App 自有 Metaobject / Metafield 定义：`{{APP_OWNED_SCHEMA}}`，未知时先检查项目配置与已有定义。

先读取项目 `AGENTS.md`、现有 `shopify.app.toml`、环境文件的**键名**、Git 状态和已有授权记录。不要输出或提交 token、client secret、密码。不要从店铺昵称、浏览器标签或旧报告猜测目标店铺。

目标是让后续 AI 在同一个店铺、同一个可识别的应用身份下，直接使用 Shopify CLI 和 Admin GraphQL 完成建站资源操作。Theme CLI 另用 Theme Access；它不能充当 Admin GraphQL 令牌。初次安装、OAuth 或增加 scopes 可能需要有权限的店铺人员在 Shopify 授权页面批准；完成后继续自动化。

## 1. 决定并固定 Admin GraphQL 身份

默认优先使用 Shopify CLI 的店铺授权来管理**店铺自有**的 Products、Collections、Menus、Pages、Blogs、Articles、Files、发布和 merchant-owned Metaobjects。这条路径不要求为了建站新写一个 App 项目：`shopify store auth` 保存授权，`shopify store execute` 执行 Admin GraphQL。记录 CLI 返回的 App 身份，后续保持一致。

CLI store auth 仍是 App 授权，不是无身份的店铺直连。CLI 保存的是在线令牌，过期或缺 scope 时需要重新运行；不要称其为永久一次性授权。如果任务包含项目 App 自有的 `$app` Metaobject / Metafield 定义或已有项目 App 所有的条目，使用**所属项目 App**管理，记录 Client ID，不能因 CLI 身份有同名 scope 就换身份操作。已有正确项目 App 时直接复用。

记录最终选用的路径及原因；同一资源不要在 CLI 身份和项目 App 身份之间随意切换。

## 2. 一次申请建站权限包

完整建站项目默认申请以下 scopes，宁可在建站开始时覆盖已知的建站工作，也不要等到商品、分类或内容阶段才逐项追加：

```toml
[access_scopes]
scopes = "write_products,write_publications,write_online_store_navigation,write_content,write_metaobjects,write_metaobject_definitions,write_files,write_inventory,read_locations"
```

上面是项目 App 的 TOML 写法；CLI 路径的 `connect:shopify` 会用同一组 scopes 调用 `shopify store auth`。

这组权限面向商品与自动 Collections、Online Store 发布、Menus、Pages / Blogs / Articles、Metaobject 定义与条目、Files、库存和地点读取。Shopify 对某些操作还可能要求额外权限或资源条件；执行前以当前 API 文档和实际返回为准，不能把权限包当作全部操作必定成功的保证。若需求超出建站范围，列出新增 scope 和用途再申请。不要加入与本项目无关的客户、订单、支付权限。

纯 Theme 项目不用为了候选 Admin API 权限创建 App；需要写入店铺资源时再运行本 Prompt。只创建 Pages / Blogs / Articles 时，`write_content` 或 Shopify 文档允许的对应页面写权限即可，但完整建站项目仍按上面的权限包一次申请。

## 3. 完成安装授权并核对真实权限

1. 检查 Shopify CLI 版本和可用命令。**CLI 路径**：在基于 Shopify-Template 的项目中运行 `npm run connect:shopify -- --store <store>.myshopify.com`。命令会先复用已保存授权；缺失或 scopes 不足时执行 `shopify store auth` 申请完整建站权限，随后通过 `shopify store execute` 读回目标店铺、当前 App 身份和实际 scopes。只有退出码为零且 `ok: true` 才继续写入。没有模板脚本的项目，按相同顺序直接运行上述两条 Shopify CLI 命令并核对返回。
2. **项目 App 路径**：把权限写入实际使用的 `shopify.app.toml`，运行 `shopify app config validate --json`，部署配置并完成安装或重新授权。明确 App 如何取得 Admin API access token：同一 Shopify 组织的 App 和店铺可用 client credentials 按需重新获取；客户店铺不在同一组织时，使用适用的 App 分发、安装与 OAuth / token exchange 流程。然后配置本地 `SHOPIFY_STORE`、`SHOPIFY_APP_CLIENT_ID` 和 `SHOPIFY_ADMIN_API_ACCESS_TOKEN`，运行 `npm run preflight:shopify -- --store <store>.myshopify.com`。不要把 CLI deploy 成功当作店铺已批准新增权限。
3. 将“计划权限”“配置或授权请求”“店铺实际获批权限”分别记录。按计划操作核验写入能力；不要仅凭缺少重复的 `read_*` 名称判定对应 `write_*` 无效。
4. 如缺权限，先检查店铺和身份，再重新运行对应的连接或授权流程。需要用户完成登录、2FA 或批准页面时，明确给出准确店铺、App 名称及待批准权限；不要声称已获批，也不要在此期间进行依赖该权限的写入。

连接检查通过后，立即继续当前导入、分类或内容创建任务；不要只报告“权限已就绪”就停止。CLI 需要打开 Shopify 授权页面时，按项目规则在已登录的 SunBrowser 中完成，不要绕过人工批准。

## 4. 验证执行通道

- 生产店铺的 GraphQL mutation 可以用已经授权的 `shopify store execute --store <store>.myshopify.com --query-file <file> --allow-mutations`，**前提是其 App 身份适合目标资源**；也可以用本项目 App 的 Admin GraphQL 客户端和有效 access token。只对 App 自有资源要求所属项目 App 身份。
- `shopify app execute` 的 mutation 仅允许开发店，不把它当作生产店铺写入通道。
- 对每次 GraphQL 写入检查顶层 `errors`、mutation `userErrors`、返回 ID 和远端读回结果。商品导入、分类和页面同步应按稳定 handle / SKU / GID 做可恢复的创建或更新。
- Theme CLI 优先使用 `SHOPIFY_CLI_THEME_TOKEN`；与 Admin API 凭据分开保存。无需为了 Admin GraphQL 工作把 Theme Access token 当作 App token，也无需为了 Theme 操作擅自启动账号登录。

## 5. 留下可复用的授权记录

在项目内现有的非敏感配置或报告位置保存：店铺域名、应用名称与 Client ID、授权路径、API 版本、计划 scopes、实际 scopes、验证时间、验证命令、Theme Access 是否已配置，以及尚待人工完成的步骤。只记录 Theme Access 是否可用，不记录其值；不要保存 access token 或 client secret。若项目没有合适位置，可建立 `docs/shopify-access.md`。

后续导入、分类或内容创建任务先读取记录，再按已选路径运行 `connect:shopify` 或 `preflight:shopify` 做实时检查。若一致，直接继续，不重建 App、不重复申请 scopes；CLI 在线令牌过期时，`connect:shopify` 会重新发起授权。项目配置可以保留并复用，但 Shopify 认证本身不能保证永久有效。

完成时明确报告：**可继续的操作、执行身份、实际 scopes、生产写入通道、Theme Access 状态、仍需店铺人员完成的授权动作**。只有真实获批并读回确认后，才能标记授权准备完成。
