# 使用 Shopify-Template 创建新项目

你现在需要基于 Shopify Template 模板创建或初始化一个新的 Shopify 项目。

模板仓库：

```text
https://github.com/zls233/Shopify-Template
```

这不是从零搭建 Shopify Framework，也不是立即实现完整店铺功能。目标是把已经在真实项目中反复出现的基础问题提前处理好，然后再进入页面复刻、商品数据和项目定制流程。

## 项目信息

执行前读取并确认以下变量：

- 原站品牌名：`{{SOURCE_BRAND_NAME}}`
- Shopify 店铺：`{{SHOPIFY_STORE}}`
- Shopify Partner 账户：使用当前操作者自己的 Shopify Partner 账户，不填写或使用原店铺账号
- 目标网站：`{{TARGET_SITE_URL}}`
- Draft Theme ID（如果已经存在）：`{{DRAFT_THEME_ID}}`；没有时留空，后续主题阶段创建 unpublished Theme。

项目名默认使用原站品牌名 `{{SOURCE_BRAND_NAME}}`。如果用户明确指定了其他项目名，以用户指定值为准；否则不要使用域名、Shopify 店铺名或通用的 `Shopify-Theme` 作为项目名。原站品牌名必须从目标网站、reference 或用户提供的信息中确认，不能根据域名或示例值猜测。

如果店铺或目标网站变量为空，不要使用示例值或猜测。原站品牌名先从目标网站确认，无法确认时停在该步骤；Draft Theme ID 允许暂时为空。

## 一、先确认工作区，不要覆盖已有项目

1. 检查当前路径、Git 状态、远程地址和已有文件。
2. 如果工作区为空，使用 GitHub 的 `Shopify-Template` 作为起点，保留完整目录结构、`AGENTS.md`、README、Theme 骨架和检查脚本。
3. 如果工作区已经是一个 Shopify 项目，不要直接覆盖用户文件。先比较当前项目和模板，只补缺失的基础文件，并保留用户已有的主题、脚本、环境配置和未提交改动。
4. 不要把模板中的示例店铺、Theme ID、token、密码、商品 ID 或分类名称复制到新项目。
5. 已配置项目目录时沿用该目录；将 `package.json` 名称更新为已确认的原站品牌名。只有明确配置 GitHub 目标时才创建远端仓库或设置 Git remote；不要把新项目的改动推回模板仓库。

模板本身是轻量起点，不要在初始化阶段新增：

- `sync-collections` 或通用资源同步框架
- Service/Repository 层
- 大型 Shopify SDK 封装
- 完整视觉回归平台
- CI/CD 工作流

只有同一个问题至少在两个真实项目中重复出现，并且解决方式稳定后，才考虑提升为模板能力。

## 二、初始化环境

1. 检查 Node.js、npm、Shopify CLI 是否可用。
2. 根据 `.env.example` 创建本地 `.env.local`。
3. 只在本地环境文件或系统凭据存储中配置：

```dotenv
SHOPIFY_STORE={{SHOPIFY_STORE}}
SHOPIFY_ADMIN_API_ACCESS_TOKEN=
SHOPIFY_APP_CLIENT_ID=
SHOPIFY_API_VERSION={{ADMIN_API_VERSION}}
SHOPIFY_STOREFRONT_URL=
SHOPIFY_THEME_ID={{DRAFT_THEME_ID}}
```

4. 不要在聊天、代码、Liquid、截图、审计报告、命令 URL 或 Git 历史中输出 token、密码或 client secret。
5. 安装模板依赖并运行基础检查：

```bash
npm install
npm run check
shopify theme check --path theme
```

如果当前项目没有 `theme/assets/theme.js` 或其他示例文件，以实际存在的文件为准，不要为了通过命令随意生成无关文件。

## 三、开工时规划并验证 Admin GraphQL 权限

如果预计本项目会导入商品、建立分类或创建 Pages / Blogs / Articles，先执行 `00-project/建站授权准备.md`，确认用户自己的 Shopify Partner 账户已获得目标店铺 Partner / Collaborator 权限，再完成一次完整建站权限包的申请、安装和真实权限核对。后续资源任务复核其结果，不重复创建应用。本节是初始化摘要；授权操作和完成标准以该独立 Prompt 为准。

先确定项目是纯 Theme 工作，还是包含商品、内容和店铺资源的完整建站。完整建站项目在首次店铺授权时申请覆盖常见建站工作的权限包，避免每进入下一阶段就增加 scope、重新授权。记录“工作范围 → 所需能力 → 执行应用身份”；后续出现建站权限包以外的新需求再补充。

完整建站项目默认申请：

```toml
[access_scopes]
scopes = "write_products,write_publications,write_online_store_navigation,write_content,write_metaobjects,write_metaobject_definitions,write_files,write_inventory,read_locations"
```

这组权限覆盖商品、变体、自动集合、Online Store 发布、菜单、Pages / Blogs / Articles、Metaobject 定义与条目、Shopify Files、库存和地点读取。Shopify 的同类 write scope 包含 read 能力，所以上述 9 个 scope 已覆盖对应的读取能力；不必把同类 `read_*` 再逐一声明。不要为了“全权限”加入与建站无关的订单、客户或支付权限。纯 Theme 项目无需申请这组 Admin GraphQL 权限，主题操作继续使用 Theme Access。

`Shopify-Template` 本身没有 `shopify.app.toml`。纯 Theme 项目无须申请 Admin API 权限；店铺自有资源可运行 `npm run connect:shopify -- --store {{SHOPIFY_STORE}}`，让 CLI 申请并核对建站权限。若需要 App 自有 Metaobject / Metafield schema 或专属应用身份，再创建或关联**本项目自己的 Shopify App**，确认其 Client ID 和目标店铺，把 scopes 写入 `shopify.app.toml`，验证、部署并完成授权。记录计划、授权请求和实际获批的三份 scope 清单；scope 不能代替资源所有权。

在任何 Shopify Admin API 写入之前，必须明确用户自己的 Partner 账户、当前 store 和 App identity；不得使用原店铺账号代替授权。店铺自有资源运行：

```bash
npm run connect:shopify -- --store {{SHOPIFY_STORE}}
```

使用项目专属 App 时运行模板校验命令：

```bash
npm run verify:shopify -- \
  --store {{SHOPIFY_STORE}} \
  --require-scope write_products
```

上面的 `write_products` 只是计划写入商品时的示例；实际校验项必须来自本项目的操作清单。不要只根据 `shopify.app.toml` 或 CLI deploy 的成功状态判断 scope 已生效，必须使用**后续执行写入的同一个身份**读取 `currentAppInstallation.accessScopes { handle }`。如果缺 scope：

1. 先确认目标 store 和 App identity 没有错。
2. CLI 路径重新运行 `connect:shopify`；项目 App 路径修改配置、运行 `shopify app config validate --json` 并执行 `shopify app deploy`。
3. 由有权限的店铺人员批准新增 scope，通过正常授权流程后再次校验。AI 不得把“已写入 TOML”或“部署成功”报告为“权限已获得”。
4. 不要换用另一个项目的 token 绕过权限问题。

店铺自有资源优先用 CLI store auth / store execute 完成 Admin GraphQL 工作；App 自有资源使用所属项目应用身份。`shopify app execute` 的 mutation 仅适用于开发店，不要作为正式店的通用写入方案。使用 CLI 身份前，确认目标资源不是另一个应用拥有的 Metaobject 定义。

## 四、SunBrowser 是后台访问硬性要求

只要任务需要通过浏览器访问 Shopify Admin、登录、OAuth、密码页或其他后台 UI：

- 必须使用已经登录的 SunBrowser。
- 不要使用 IAB、普通 Chrome、其他浏览器 profile 或临时浏览器会话替代。
- 不要自动化登录、2FA、CAPTCHA 或绕过账号验证。
- 使用当前操作者自己的 Shopify Partner 账户；如果该账户尚未获得目标店铺权限，暂停并请求店铺人员完成 Partner / Collaborator 邀请。
- 店铺密码只允许作为当前 SunBrowser 会话中的临时输入，不写入项目或长期保存。

如果 API 或 Shopify CLI 可以完成同一操作，优先使用 API/CLI；只有认证或 UI-only 操作才使用 SunBrowser。

## 五、Theme 开发边界

1. 默认只使用 Draft/Development Theme：

```bash
shopify theme dev \
  --store {{SHOPIFY_STORE}} \
  --path theme \
  --theme {{DRAFT_THEME_ID}}
```

2. 不要在没有明确授权时发布 Live Theme、覆盖线上主题、删除商品或删除 Collections。
3. Header、Mega Menu 和移动导航使用 Shopify Menu 的 `section.settings.menu.links` 与 `link.links`，不要在 Liquid/JavaScript 里维护第二套导航树。
4. Collection 页面使用真实 `collection.products`，保留 Shopify 原生排序、筛选、分页、价格、库存和商品链接。
5. 变体使用真实的 `product.variants`、`variant.options`、`variant.featured_media` 和 `selected_or_first_available_variant`，不要根据图片文件名猜测颜色或 Variant。
6. 可选 Metaobject 为空时使用 Shopify 原生对象作为安全回退。

## 六、最小交互验证

模板只提供最小 storefront smoke test。配置 `SHOPIFY_STOREFRONT_URL` 后运行：

```bash
npm run test:smoke
```

它只验证页面可以响应、文档可见且正文不为空，不替代项目级交互验收。

如果任务涉及参考网站复刻，后续再按需要使用 `01-reference/页面爬取.md`、`02-theme/开始复刻.md`、页面专项 Prompt 和 `05-qa/交付评估.md`。只有实际需要时才新增 `interaction-audit.md`、Playwright 断言或项目专用脚本，不要在初始化阶段提前建设完整视觉回归系统。

## 七、完成初始化后的报告

完成后输出：

- 项目路径和 Git remote
- 模板来源和初始化方式
- Store domain、App identity、已安装 scopes
- Draft Theme ID 与当前是否为 Live Theme
- 新增或保留的文件
- `npm run check`、Theme Check 和 smoke test 结果
- 尚未完成的登录、授权、环境配置或用户确认步骤

初始化完成后，项目才可以进入页面采集、Theme 复刻、商品数据导入、分类导航配置或定制开发阶段。
