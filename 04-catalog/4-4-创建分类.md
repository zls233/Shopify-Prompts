# 默认商品状态与库存前置条件

在读取分类/菜单数据前，按 `STAGE_COMPLETION_CONTRACT.md` 先核对同一目标店铺的全部商品状态为 ACTIVE，并将全部可跟踪库存变体在已核验地点的 available 设为 9999；状态/库存和前台 Collection publication 是不同层次，不能用 ACTIVE 代替实际发布渠道的验证。4-4 仍须为全量来源商品做分类对账，源站未能采集的商品不能假装已导入。

开始本任务前，先执行或复核 `01-project/1-2-建站授权准备.md`。确认目标店铺、执行 App 身份，以及商品、Collections、Menus、发布和 Metaobjects 所需的实际授权；缺失时先完成授权，再写入资源。已有有效授权时直接复用，不重复创建应用。

分析当前 Shopify 主题和参考页面的完整导航与商品分类结构，然后根据页面实际结构配置 Shopify 的 Products、Collections、Menus、Metaobjects 和主题导航。

先读取 `EXECUTION_RULES.md`。建立 Header/Mega Menu/Mobile 全部一级、二级、三级入口清单，逐条记录标签、层级、源 URL、目标 Collection handle/GID 和实际访问结果；对重复目的地去重采集，但每条菜单链接都要核验。

## 原站分类对账与范围

- 统一源站快照时间，对每个分类抓取全部分页成员，以源 handle 和目标 handle 映射对账 `missing / extra`。不能只看总数，也不能只验证已导入目录与源站的交集。
- 区分原站全目录、当前已导入目录和历史商品。未导入的源商品交给 `4-3-导入商品.md`；原站下架/历史成员单列，不擅自删除、归档或下架。只要求“分类效果一致”时不额外要求排列完全一致，视觉与交互仍单独对照。
- 商品可命中多个分类。品类与 New Arrivals、Best Sellers、Sale 等专题分别取证；不用宽泛标题正则或单一 `TYPE EQUALS` 代替实际成员依据，也不因四折价格变化就把全目录自动当成原站 Sale。
- 优先复用稳定 handle、原生自动集合和有证据的分类字段；已有手动集合可按当前任务保留。报告“当前快照成员一致”和“未来商品自动分类”各自结果，不把手动快照称为自动分类完成。
- 分类、菜单、商品标签和筛选配置为共享店铺数据，可能影响 Live，即使 Theme 文件只推 Draft 也必须记录这些变化。

## 从首页逐分类检查的前台闭环（与 6-6 衔接）

后台成员对账不能替代真实前台检查。为所有 Header / Mega Menu / Mobile 商品分类建立可执行的点击清单，记录原站层级、源 URL、目标 Collection、全量成员差集和分类语义；确保每个商品归属于原站对应分类，**不要求商品排列一致**，但漏分、错分、空卡、坏图和分页不完整都必须修复。此处先完成全量商品/集合/菜单数据层校准，主题可访问后按 `06-qa/6-6-首页导航逐分类商品对照与修复.md` 逐条进入两站首页导航实测并修复。若 4-4 阶段尚未构建可用 Draft，保存待执行的逐分类验收清单交给 FAST 6-1；**不能把后台通过冒充最终前台分类 QA 已通过**。

## 筛选数据和后台配置

先核对真实商品的颜色、尺码、价格/可售字段与 `collection.filters`；分别定位字段缺失、分类漏分、后台未启用、主题渲染或 URL 行为问题。需要 Search & Discovery 时先复用现有安装和当前项目明确的安装授权，未获必要授权则记录依赖，不反复创建 App。源站宽泛颜色组与历史细分颜色标签不自动等价，保留来源和规范化映射，不能按图片名猜颜色或假造筛选选项。

原生筛选、排序和分页要验证结果成员、计数与 URL 参数；切换排序保留筛选，分页保留条件，清除筛选/浏览器返回恢复正确状态。只有控件可见不算可用。

目标是实现：

用户在网页导航中点击某个品类，例如：

Women → Clothing → Pants

能够进入对应 Collection 页面，并且只显示属于该分类的商品。

具体要求：

首先分析参考页面现有的 Header、Mega Menu、Footer、Collection 页面和商品页面，提取完整 taxonomy / category hierarchy。
不要只修改前端写死导航。优先使用 Shopify 原生数据结构实现：
Products：商品本身
Tags / Product Type / Metafields：商品分类属性
Automated Collections：商品集合
Menus：导航结构
Metaobjects：Mega Menu、分类 Banner、图片、文案等结构化内容
扫描当前 Shopify 店铺中的所有商品，根据商品：
title
product type
tags
vendor
description
existing metafields
判断其所属分类。
分类不是互斥枚举：一个商品可以同时命中多个真实分类（例如 Shirts & Button Downs 与 Outerwear）。分类计划必须保存每个商品的全部命中分类、证据、`reviewRequired` 和预期集合成员，不得因为“只能选一个分类”而静默丢弃交叉归属。
建立统一、可维护的商品分类规则。
优先使用标准化 tags，例如：

gender:men

category:accessories

subcategory:pants
subcategory:dresses
subcategory:sweaters
subcategory:sandals

根据实际商品和参考站 taxonomy 扩展。

为商品补充缺失的分类 tags / product type / metafields。
不要为了当前页面效果手动把商品 ID 写入主题。

对照原站已有分类或专题集合时，必须按稳定 handle 对账完整成员集合，输出 `missing` / `extra`，不能只比较 `productsCount`。目标是精确校准时，先生成 dry-run 计划和 source 快照；多余成员优先通过证据充分的分类修正，必要时使用带日期和责任范围的命名空间排除标签加 `TAG NOT_EQUALS`，不得删除无关标签、归档商品或在主题中筛掉商品。
